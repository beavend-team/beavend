# Beavend API Specification

> **Status:** Draft / Design Contract (v0.1)  
> Single source of truth: `api/openapi.yaml` (OpenAPI 3.1)

---

## 1. Overview & Protocol Conventions

Beavend exposes two distinct API surfaces:
1. **Runtime API (Data Plane):** High-throughput, low-latency endpoints consumed by client SDKs (Android, iOS, Web) on behalf of authenticated end users.
2. **Management API (Control Plane):** Administrative endpoints consumed by the admin dashboard and automation tooling to configure projects, AI Apps, models, prompts, policies, and tools.

### 1.1 Base URLs
* Runtime Plane: `https://<beavend-host>/v1`
* Management Plane: `https://<beavend-host>/v1/admin`

### 1.2 Common Request Headers
| Header | Type | Description | Required |
|---|---|---|---|
| `Authorization` | String | `Bearer <user-jwt>` (Runtime) or `Bearer <admin-token>` / Session (Admin) | Yes |
| `X-Project-ID` | String | Identifier of the tenant project (e.g., `proj_ecommerce_prod`) | Yes |
| `X-Environment` | String | Target environment (`development`, `staging`, `production`) | Yes |
| `X-Request-Id` | String | Unique client request identifier (`req_<uuid>` or generated by server) | Optional |
| `X-Beavend-SDK-Version` | String | Client SDK identifier and version (e.g., `kmp/0.1.0`, `ios/0.1.0`) | Recommended |

### 1.3 Identifiers & Prefixes
All primary entities use prefixed identifiers for auditability:
* `req_`: Request ID (e.g., `req_01HP3KX...`)
* `proj_`: Project ID (e.g., `proj_mobile_app`)
* `app_`: AI App ID (e.g., `assistant`, `document-analyzer`)
* `tool_`: Tool ID (e.g., `tool_get_orders`)
* `pv_`: Prompt version (e.g., `pv_01HP...`)

### 1.4 Response Envelope & Content Types
* Standard JSON endpoints: `Content-Type: application/json`
* Streaming endpoints: `Content-Type: text/event-stream; charset=utf-8`
* All error responses adhere to the standard Error Structure (§6).

## 2. Health & Readiness Endpoints

These endpoints are mounted on root without authentication for container probes and load balancers:

### `GET /healthz`
Liveness probe. Indicates that the HTTP process is running.
* **Response `200 OK`**: `{"status": "ok"}`

### `GET /readyz`
Readiness probe. Verifies that the instance has loaded its initial config snapshot and can connect to essential dependencies.
* **Response `200 OK`**:
  ```json
  {
    "status": "ready",
    "role": "all",
    "snapshot_revision": 42,
    "redis": "connected",
    "postgres": "connected"
  }
  ```
* **Response `503 Service Unavailable`**: Returned if the snapshot has not finished compiling or critical dependencies fail.

## 3. Runtime API Endpoints

### 3.1 Unary Chat Completion
Executes a synchronous, non-streaming request against the specified AI App.

```http
POST /v1/apps/{ai_app_id}/chat
```

#### Request Body
```json
{
  "messages": [
    {
      "role": "user",
      "content": "What is the status of my order #9872?"
    }
  ],
  "attachments": [],
  "metadata": {
    "device_locale": "en-US"
  }
}
```

#### Response `200 OK`
```json
{
  "id": "chat_01HP4AB...",
  "request_id": "req_01HP4AB...",
  "ai_app_id": "assistant",
  "created_at": 1711200000,
  "message": {
    "role": "assistant",
    "content": "Your order #9872 was shipped on March 22 via Express Post."
  },
  "finish_reason": "stop",
  "usage": {
    "input_tokens": 142,
    "output_tokens": 28,
    "total_tokens": 170
  }
}
```

---

### 3.2 Streaming Chat Completion (SSE)
Establishes a Server-Sent Events (SSE) stream for low-latency token delivery.

```http
POST /v1/apps/{ai_app_id}/stream
```

#### Request Body
Same as `POST /v1/apps/{ai_app_id}/chat`.

#### SSE Protocol & Event Types
The stream returns events formatted as `event: <name>\ndata: <json>\n\n`:

1. **`delta`**: Streamed text chunk.
   ```text
   event: delta
   data: {"text": "Your order "}
   ```
2. **`tool_call`**: Emitted when a **client-side tool** must be executed on the client device.
   ```text
   event: tool_call
   data: {"call_id": "call_123", "tool": "open_screen", "args": {"screen": "orders"}}
   ```
3. **`confirmation`**: Emitted when a write tool requires explicit human-in-the-loop approval.
   ```text
   event: confirmation
   data: {"tool": "cancel_order", "args": {"order_id": "9872"}, "token": "eyJh..."}
   ```
4. **`usage`**: Emitted prior to stream completion with token consumption statistics.
   ```text
   event: usage
   data: {"input_tokens": 142, "output_tokens": 28, "total_tokens": 170}
   ```
5. **`error`**: Emitted if a downstream error occurs after streaming has begun.
   ```text
   event: error
   data: {"code": "provider_error", "message": "Upstream model timed out"}
   ```
6. **`done`**: Final event signaling clean stream termination.
   ```text
   event: done
   data: {"request_id": "req_01HP4AB..."}
   ```

### 3.3 Confirm Suspended Tool Execution
Resumes a request that was paused awaiting explicit user confirmation.

```http
POST /v1/apps/{ai_app_id}/confirm
```

#### Request Body
```json
{
  "confirmation_token": "eyJh...",
  "approved": true
}
```

#### Behavior
* If `approved: true`, the runtime re-validates the token, verifies that the user matches the original caller, executes the bound tool with the frozen arguments, and streams or returns the continued response.
* If `approved: false`, the runtime discards the pending state and returns a cancellation status.

---

### 3.4 Submit Client-Side Tool Results
Submits the execution output of a client-side tool requested by the model.

```http
POST /v1/apps/{ai_app_id}/tool-results
```

#### Request Body
```json
{
  "continuation_token": "eyJh...",
  "call_id": "call_123",
  "result": {
    "status": "success",
    "screen_opened": true
  }
}
```

---

### 3.5 Cancel Active Request
Explicitly requests cancellation of an in-flight stream or background operation.

```http
POST /v1/apps/{ai_app_id}/cancel
```

#### Request Body
```json
{
  "request_id": "req_01HP4AB..."
}
```

---

### 3.6 Inspect AI App Metadata
Returns public configuration metadata for an AI App (does not leak system prompts or keys).

```http
GET /v1/apps/{ai_app_id}
```

#### Response `200 OK`
```json
{
  "id": "assistant",
  "name": "Customer Support Assistant",
  "description": "Helps users with account and order queries",
  "client_tools": [
    {
      "name": "open_screen",
      "description": "Navigates to an in-app view",
      "parameters": {
        "type": "object",
        "properties": {
          "screen": { "type": "string" }
        },
        "required": ["screen"]
      }
    }
  ]
}
```

### 3.7 Memory Endpoints (Opt-in, v0.3)
Scoped to `project + issuer + subject + ai_app_id`.

* `GET /v1/apps/{ai_app_id}/memory` — Fetch active memory entries for the caller.
* `POST /v1/apps/{ai_app_id}/memory` — Explicitly upsert a semantic memory entry.

## 4. Management API Overview (`/v1/admin`)

Management endpoints require administrative authentication (Bearer admin token or session cookie) with RBAC roles (`owner`, `editor`, `viewer`).

| Path | Methods | Description |
|---|---|---|
| `/v1/admin/projects` | `GET`, `POST`, `PUT` | Manage tenant projects and environments |
| `/v1/admin/apps` | `GET`, `POST`, `PUT`, `DELETE` | Configure AI Apps, assigned prompts, models, and tools |
| `/v1/admin/providers` | `GET`, `POST`, `PUT`, `DELETE` | Configure LiteLLM credentials and native provider connections |
| `/v1/admin/models` | `GET`, `POST`, `PUT` | Manage logical model aliases (`fast`, `reasoning`, `vision`) |
| `/v1/admin/prompts` | `GET`, `POST` | Create and publish immutable prompt versions |
| `/v1/admin/tools` | `GET`, `POST`, `PUT` | Manage custom tools, JSON schemas, identity bindings, and executors |
| `/v1/admin/guardrails`| `GET`, `POST`, `PUT` | Define input and output safety guardrails |
| `/v1/admin/policies` | `GET`, `POST`, `PUT` | Configure CEL authorization policies |
| `/v1/admin/usage` | `GET` | Query aggregated usage rollups and token costs |
| `/v1/admin/logs` | `GET` | Search and inspect request metadata logs |
| `/v1/admin/subjects/{issuer}/{subject}` | `DELETE` | **Privacy Purge:** Delete all memory, threads, cache, and logs for a subject |

## 5. Client vs. Server Responsibilities

| Responsibility | Server (Beavend) | Client SDK |
|---|---|---|
| Identity Validation | Verifies JWT signature, expiration, issuer, audience | Obtains token from IdP via callback and attaches to header |
| Provider Keys & Models | Stored securely server-side; maps logical to real models | Zero knowledge of provider keys, deployments, or raw models |
| System Prompts & Versioning | Maintained server-side with immutable versioning | Only passes user-level conversation turns |
| Tools & Data Access | Authorizes, binds user ID, calls backend API, sanitizes output | Executes registered UI/device tools when requested |
| Rate Limits & Quotas | Atomic multi-window limit enforcement (Redis Lua) | Respects `retry_after` headers on `429` |
| Streaming | Native HTTP/2 SSE flusher with heartbeats | Reads `AsyncSequence` / `Flow`, handles reconnects |

## 6. Error Taxonomy & RFC 7807 Structure

All errors returned by Beavend follow this uniform JSON structure:

```json
{
  "code": "rate_limited",
  "message": "Daily inference quota exceeded for tier [free]",
  "request_id": "req_01HP5Q...",
  "retry_after": 3600,
  "details": {
    "resource": "inference",
    "window": "24h",
    "limit": 30,
    "current": 30
  }
}
```

### Standard Error Codes

| HTTP Status | Code | Meaning & Actionable Remedy |
|---|---|---|
| `400 Bad Request` | `invalid_request` | Malformed JSON or input failing schema validation. |
| `401 Unauthorized` | `unauthenticated` | Missing, expired, or invalid JWT signature. Client must refresh token. |
| `403 Forbidden` | `forbidden` | Authorization policy denied access to the AI App or Tool. |
| `404 Not Found` | `not_found` | Unknown AI App ID or Project ID. |
| `422 Unprocessable` | `guardrail_blocked` | Input or output guardrail blocked request (e.g. injection, PII). |
| `429 Too Many Requests`| `rate_limited` | Quota or rate limit exceeded. `retry_after` specifies wait seconds. |
| `502 Bad Gateway` | `provider_error` | Upstream model provider failed or returned invalid response. |
| `503 Unavailable` | `unavailable` | Dependency (Redis/LiteLLM) is down (fail-closed mode). |
| `504 Gateway Timeout` | `tool_timeout` | Downstream tool executor exceeded timeout budget. |
